# 0015. 文件与后台生命周期可靠性、输入运行时隔离

- 状态：本分支已实现，待合并审核
- 日期：2026-11-05

## 问题

正常输入流程之外，文件提交与确认、两条连接之间的取消顺序、引擎及 UI 重启会产生不同生命周期。
单线程 Tokio 上同步调用剪贴板和系统检查，还会把与输入无关的耗时带到键鼠与心跳任务。

## 决策

继续使用 TCP + TLS 1.3，保留现有 crate 层级和输入顺序。没有切换 QUIC、增加固定输入等待或丢弃键鼠事件。

### 文件提交与任务状态

- 在 `ferry-platform` 增加 `FileCommit` trait，各平台同名文件实现。macOS 使用 `renamex_np(RENAME_EXCL)`；
  Windows 使用不带替换和跨卷复制选项的 `MoveFileExW`，目标存在时重选名字。
- 跨盘内容先复制到目标卷唯一隐藏目录，最后原子提交。取消只影响尚未提交的阶段；已经公开的文件不回滚删除。
  多项任务中途失败时保留已经公开的项目，并明确报告部分保存。
- 文件任务区分尝试代次，重复 Offer/Accept 幂等；独立 File 连接失败可以重试，无需等整个输入会话重连。
- 接收任务保留绑定设备身份的完成/取消信息。收到 EOF 后的迟到取消仍能清理；完成确认丢失后重放结果，不重复落盘。
- `partial/` 内改用 `<设备指纹>/<传输号>/` 隔离任务，`committed.json` 保存清单指纹和最终路径。
  完成的 payload 删除，回执留在缓存。用户清缓存后不能继续保证同 ID 的完成去重。
- 文件任务上限为全局 64、每设备 8；发送清单扫描最多同时 2 个。清单数量和总字节需与 Offer 对应，拒绝零进展循环。

旧版未完成缓存的布局不迁移；发送任务原本也不跨进程持久化，升级时未完成传输需重新发起。
本实现不提供“目标改名和回执文件持久化”之间跨目录的掉电事务保证；普通断线、重连和最终确认丢失已覆盖。

### 后台、数据连接与工作线程

- 保留单线程 Tokio 的输入状态机；剪贴板系统操作交给每端的专用串行线程，用有界队列异步等待结果。
  已取消且尚未执行的请求跳过；已经开始的原生系统调用无法强行中断。
- 输入循环不再等待 Data 连接。Data 独立建立并按上限 30 秒退避重连；恢复时由当前活动端通告内容，避免旧剪贴板覆盖。
- 服务端使用任务集合跟踪握手并限制并发，停止时取消未完成任务；后台通过引擎代次丢弃旧事件和配对请求。
- 使用操作系统文件锁保证每数据目录只有一个后台；锁文件不删除，进程结束释放锁。
  `instance.lock` 位于缓存目录。更新时在后台工作任务结束后释放锁，再启动新版本。
- 文件准备、日志读取、诊断和预览写盘通过后台任务完成事件回报。日志每窗口只允许一项在飞；预览串行并合并最新请求。
- 快照仅使用缓存的安装能力、地址和自然滚动信息；地址及自然滚动按 30 秒低频刷新，安装执行前再次检查资格。
- 浮层输入更新目标状态，绘制受帧截止时间控制。过期提示计时在拖出文件期间暂停；原生刷新合并。

### UI 和更新

- 本机 IPC 升至 3；State 与配对提示包含后台随机 session。
  `Execute` 绑定 session 和请求编号，后台先同步真实 State 再回复 `CommandResult`。
- 配对回复必须包在 Execute 内；旧 session、嵌套 Execute、已结束配对请求不会被执行。
- 异步连接/邀请由后台操作号映射到原窗口及 UI 请求号，两个窗口相同编号不互相干扰。
- IPC 断线时关闭旧配对提示并撤销乐观状态；等待 Welcome 有超时；强调色越界安全回退。
- 更新自动失败进入退避，未成功检查不能宣称最新。安装资格异步查询并缓存。
- Windows 在禁止写入/删除的句柄保护下重新核对签名清单的大小和 SHA-256，并保持句柄直到启动返回。
- 更新健康探测使用独立、带随机 endpoint 令牌的请求并验证目标应用版本，不要求 UI IPC 版本相同。

## 兼容性与验证

设备间的线协议版本仍为 1，新增检查落实已协商能力。UI 与后台需同包升级（IPC 3）。
旧对端不具备新的接收回执与故障修复，两台升级后才能取得双端收益。

新增测试覆盖：并行原子提交、跨盘取消、部分提交失败保留用户改动、确认丢失、EOF/Cancel 乱序、独立 File/Data 失败、
活动剪贴板恢复、阻塞原生剪贴板时输入继续、浮层过期和帧上限、配对暂停/重启、UI 失败回滚、多窗口结果路由、
并发后台启动、诊断阻塞时暂停可用、跨 IPC 健康检查和更新失败退避。

Windows GUI 与 macOS 实际辅助功能/拖放仍需双机验收。此变更未承诺某个毫秒延迟，Wi-Fi 的 p95/p99 改善需实测。
