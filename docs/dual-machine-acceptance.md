## 2. 测试约定与数据

- 方向 A：Mac 控制 Windows。方向 B：Windows 控制 Mac。先完成 A，再在“设置 → 这台电脑”切换双方角色完成 B；不要把两台同时设为控制端来替代双向验收。
- 每个写着“A、B”的用例两方向都做；只完成一个方向时结果记“部分执行”，不能记整体通过。
- 结果取值：未执行、通过、失败、部分执行、受阻、不适用。失败必须记录步骤、时间、实际现象和诊断路径；不适用必须说明环境原因。
- 任何误触、卡键、光标丢失、已有文件被改写、内容校验不一致均记失败。先用本地键鼠恢复，再导出诊断；不要反复重启掩盖故障。
- 强制返回快捷键：Mac 为控制端时 `Ctrl + Option + Esc`；Windows 为控制端时 `Ctrl + Alt + Esc`。正式测试前让本地操作者知道这一操作。
- 为本轮准备带独特前缀的可丢弃文件：中英文文本、PNG、带格式文本、空文件、含子目录和空目录的文件夹，以及在当前网络上足以观察进度的大文件。不要使用真实私密内容。
- 准备两份来自不同源目录、文件名相同而内容不同的文件；接收端“下载”另放一份同名哨兵文件。记录三份文件的 SHA-256。准备同名文件夹时，哨兵文件夹内也放一个可校验文件。
- 文件落点默认是系统“下载”。观察接收状态时不要移动或删除正在传输的测试内容。测试多次后用本轮前缀、时间及哈希识别产物，避免把旧产物当作本次成功。

核对单文件内容可以使用系统命令，路径换成实际测试文件：

```bash
# Mac
shasum -a 256 "/实际路径/测试文件"
```

```powershell
# Windows PowerShell
Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\实际路径\测试文件'
```

目录传输逐项核对相对路径、文件数量、空目录和文件哈希。`.DS_Store`、`Thumbs.db`、`desktop.ini` 属于有意跳过的系统文件；目录内符号链接也不纳入“所有文件都应传输”的预期。

## 5. Wi-Fi 观察与延迟结论

在用户实际 Wi-Fi 上完成上述验收，只能支持该环境下的功能与恢复结论，**不等于证明修复降低了输入延迟**。两条 TCP 连接及独立文件连接仍共享无线链路，传大文件时也可能有无线拥塞。

如果要比较延迟，需要另做旧版与修复版对照：固定两台机器、角色、AP、网络频段、距离、输入动作和传输负载，记录采样方法、时长及样本数，分别报告 p50 / p95 / p99。程序显示的往返时间是应用层 Ping/Pong RTT，包含调度与排队，不能当作纯网络 RTT 或端到端输入显示延迟。首轮不要从屏幕上的少量 RTT 值推算 p95/p99 或宣称固定百分比收益。
